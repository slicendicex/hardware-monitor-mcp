# Инструкции coding-агентам

В WSL прочитай локальные инструкции `~/.codex/RTK.md` и используй `rtk` для команд оболочки.

## Начало сессии

С уже загруженными инструкциями прочитай [оперативное состояние](docs/PROJECT_STATE.md) и проверь `rtk git status --short --branch`. Сопоставь ближайший шаг с запросом пользователя. Уже доступные документы перечитывай только при изменении или нехватке контекста.

| Задача | Что открыть дополнительно |
|---|---|
| Новая версия | Строку версии в [ROADMAP.md](ROADMAP.md) и релевантный раздел [архитектуры](docs/ARCHITECTURE.md). |
| Архитектурное изменение | Описание затронутого компонента и соответствующие [ADR](docs/decisions/). |
| Отладка | Подходящую запись [LESSONS.md](docs/LESSONS.md). |
| Анализ истории | [CHANGELOG.md](CHANGELOG.md) и нужный фрагмент истории Git. |
| Изменение поведения | Исходный код затронутого модуля и его тесты. |

## Разработка версии

1. Сверь границы версии с ROADMAP.md. Согласуй концептуальные изменения карты с пользователем.
2. Составь план реализации.
3. Изучи релевантные модули.
4. Реализуй согласованный объём.
5. Добавь или обнови тесты.
6. Проверь совместимость существующих инструментов и форматов.
7. Запусти доступные тесты.
8. Обнови затронутую документацию и PROJECT_STATE.md.
9. Дай краткий отчёт с результатами и оставшимися ограничениями.

Приступай к следующей версии только по указанию пользователя.

## Среда и безопасность

Разработка ведётся в WSL Ubuntu через Codex CLI. Целевая среда исполнения — Windows с Python 3.14. Тесты WSL характеризуют только среду WSL. Аппаратные показания подтверждай запуском в Windows.

Сервер слушает исключительно `http://127.0.0.1:8765/mcp` через Streamable HTTP. Внешнее подключение обслуживает OpenAI Secure MCP Tunnel с клиентом в Windows. Внешний сетевой доступ требует прокси.

- В v0.1 предоставляй через MCP только чтение аппаратной телеметрии. Исключи произвольные команды, неограниченный доступ к файловой системе и изменение аппаратных настроек.
- Сохраняй привязку к loopback и проверку TLS. Оставь существующую конфигурацию туннеля и правила Windows Firewall в ведении пользователя.
- Исключи ключи API, реквизиты прокси и идентификаторы туннеля из Git.
- Перед коммитом проверь список и содержимое индексированных изменений через `git diff --cached --name-status` и `git diff --cached`. Проверь фактические имя и почту автора и коммитера локально через `git var GIT_AUTHOR_IDENT` и `git var GIT_COMMITTER_IDENT`. Используй согласованные публичное имя и адрес GitHub noreply. Не выводи личные значения в отчёт.
- Коммит, push и публикация требуют явного указания пользователя.

Состояние приложения включает, например, активный сеанс сбора или записи собственной базы метрик. К состоянию хоста относятся настройки оборудования, ОС и сети. Для будущего управления сеансом, записи метрик или запуска бенчмарка отдельно спроектируй и согласуй каждое новое полномочие MCP, его побочные эффекты и аннотации при работе над соответствующей версией. Пункт дорожной карты сам по себе полномочий не предоставляет.

## Управление контекстом

Опирайся на рабочее дерево и воспроизводимые проверки. Новая сессия должна обходиться без переписки. Храни направление проекта в ROADMAP.md, текущий факт и следующий шаг в PROJECT_STATE.md, устройство реализации в ARCHITECTURE.md, изменения версий в CHANGELOG.md. Используй ссылки вместо копирования разделов.

Фактическое поведение проверяй по коду, конфигурации и тестам. Утверждённые цели и ограничения заданы ROADMAP.md и AGENTS.md. При расхождении запиши его в PROJECT_STATE.md и согласуй изменение ограничений с пользователем. Помечай внешние результаты с указанием источника.

После существенной задачи замени устаревшие сведения в PROJECT_STATE.md. Ориентир — до 100 строк или около 1500 токенов. Различай проверенные результаты, предположения и планы. Указывай известные ограничения, неудачные и невыполненные проверки.

## Завершение версии

1. Сопоставь реализацию с каждым критерием готовности версии в ROADMAP.md.
2. Выполни доступные тесты и укажи среду запуска.
3. Зафиксируй результаты и ограничения в PROJECT_STATE.md.
4. Обнови CHANGELOG.md и, при изменении архитектуры, ARCHITECTURE.md.
5. После проверки критериев обнови статус версии в ROADMAP.md и укажи следующую запланированную версию в PROJECT_STATE.md.
6. Существенное архитектурное решение оформи новым ADR. При замене сохрани предыдущую запись, обнови её статус и свяжи обе записи. Дополняй LESSONS.md только новым воспроизводимым опытом.
7. Проверь относительные ссылки и якоря между документами.
